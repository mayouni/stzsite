Système de test et de qualité

Des gardes narrés comme spécifications, numpy et LAPACK pour oracles, une porte adversariale avec contrôles négatifs, une seule porte de règles ; ni couverture ni intégration continue.

Où il en est

La lecture du Compas Softanza : chaque couloir du domaine noté face au meilleur de sa catégorie, d'après ce que les gardes prouvent (Read from the source on 2026-09-17, from a read-only main worktree -- base/test/_narrated (455 guards), base/meta/promises.py (~8,500 #--> markers), engine test blocks (151/371 files), fuzzers and props, _gen_numpy_reference.py, plot.zig, stzRuleReport + stzPredicateSet, health in base/test/_STATUS.md / _FINDINGS.md). Les phrases du Compas sont en anglais, telles qu'il les a écrites.

Softanza has no test framework as a module — it has a test-and-quality discipline spread across the estate, and its signature is that a test is a readable specification and a green checkmark is never enough. 455 narrated guards read as Given/When/Then specs; correctness is proven against independent numpy/LAPACK oracles (not just self-captured snapshots), by byte-parity against pre-port ground truth, and by an adversarial gate whose 1,416 assertions each exist because "a defect survived a green suite" — with 58 negative controls that prove the instrument itself can fail. Distribution is tested on real spawned processes; the engine is fuzzed and property-tested; and one rule gate collects code, security, agent and diagram findings in a single shape. Where it's thin: property/mutation is engine-only, there is no coverage instrumentation and no CI, and the classic suites carry a fidelity backlog.

The honesty line on the ratings. This page rates a cross-cutting system, not a module — there is no base/test-framework; it is ~6 harnesses/gates plus a large guard corpus. Read from main. The strengths are technique-level and real (455 narrated guards; plot.zig byte-parity; numpy/LAPACK oracles; gg_adversarial's 1,416 assertions + 58 negative controls + 82 plan-discharges; D0–D6 real-process; 5 engine fuzzers + 3 property/mutation files; the 13-domain rule gate). The weaknesses are tooling-level and honestly recorded in the repo's own health files (base/test/_STATUS.md / _FINDINGS.md): no coverage %, no CI, and the classic-suite backlog. The split is the story: the curated narrated / adversarial / oracle surface is green and maintained; the classic extracted suites are the grind.

The one-sentence position. Softanza tests the way it builds — narrated as a spec, proven against independent oracles and negative controls, gated in one place — a testing discipline more rigorous than most frameworks demand; what it lacks is the ordinary tooling those frameworks ship for free: coverage numbers, a CI that runs the gate, and a reconciled classic-suite corpus.

Ce qu'un artisan en fait, et ce qui se distingue

  • A test is a readable specification: 455 narrated Given/When/Then guards
  • Correctness proven against independent numpy/LAPACK oracles, not self-captured snapshots
  • An adversarial gate of 1,416 assertions each born from an escaped defect, with 58 negative controls
  • One rule gate collecting code, security, agent and diagram findings in a single shape

Ce qui est dû

  • A standard CI pipeline running the rule gate on every push
  • Coverage instrumentation (line/branch) for the engine and guards
  • Haro-side property testing and a shipped assertion module
  • Close the fidelity-grind backlog (1,312 #ERR in the classic suites)

Repensé depuis les premiers principes

Ce que Softanza a gardé de ce qui marche, et ce qu'elle a repensé, tel que la bibliothèque l'a écrit dans ses documents de conception et ses narrations.

La manière SoftanzaChaque valeur attendue écrite est une promesse, et elle ne compte que lorsqu'une exécution qui aurait pu échouer l'a tenue.

Gardé des meilleures pratiques

  • Les tests sont des scénarios Given, When, Then : la sortie se lit comme une spécification, et un échec montre la valeur attendue et la valeur obtenue. source(s'ouvre dans un nouvel onglet)
  • Les analyseurs du moteur exposés aux entrées hostiles passent au fuzzing, et les tests de propriétés sont vérifiés par mutation : des versions volontairement fausses doivent échouer. source(s'ouvre dans un nouvel onglet)
  • Les résultats sont comparés à une référence indépendante : des valeurs produites par NumPy pour les matrices, et par R pour les lissages statistiques. source(s'ouvre dans un nouvel onglet)

Repensé

  • Des milliers de lignes d'exemple notent ce qu'elles doivent afficher. Personne ne les comparait : un banc d'essai exécute désormais chaque fichier et vérifie ces promesses dans l'ordre. source(s'ouvre dans un nouvel onglet)
  • Un test qui ne peut que réussir ne prouve rien : tout cas positif a son jumeau négatif, et l'outil est essayé sur de fausses promesses, pour le voir échouer. source(s'ouvre dans un nouvel onglet)
  • Une identité n'est pas une vérification : une formule tirée d'un seul jeu de chiffres ne peut jamais échouer. Une vraie vérification compare deux mesures indépendantes d'une même réalité. source(s'ouvre dans un nouvel onglet)
  • La suite complète est une barrière passée une fois avant chaque commit, pas après chaque modification. Les nouveaux contrôles naissent en sondes isolées : verdict en quelques secondes. source(s'ouvre dans un nouvel onglet)

12 couloirs, chacun face au meilleur de sa catégorie

Pour chaque couloir : ce qui tourne dans le moteur aujourd'hui, les outils contre lesquels il est juste de le mesurer, et ce qui reste dû.

01Narrated guards as executable specStrong

In the engine

_narrated.ring gives a Given/When/Then DSL (Scenario / Then(text, got, want) / Summary) that prints a readable spec and distinguishes "ran-but-failed" from "didn't run" — across 455 *_narrated.ring guards and on the order of 10,000+ assertions.

Measured against

CucumberRSpecjest describe/it

To complete

BDD-as-default at estate scale. The one wart: the dominant per-file chk(label, cond) idiom is copy-pasted, not imported — a convention rather than one shipped assertion module (lane 12).

02Reference oracles (numpy / LAPACK)Strong

In the engine

Correctness checked against an independent implementation, not self-consistency: _gen_numpy_reference.py generates _numpy_reference.ring / _numpy_fft_reference.ring (LAPACK eigenvalues, SVD, det, Cholesky…), and the BERT forward matches numpy to 1.64e-7.

Measured against

(rare — most suites self-check)SciPy test oracles

To complete

Oracle testing catches bugs a snapshot cannot — a snapshot pins whatever you produced, right or wrong; an oracle pins what is correct. A gold-standard technique used where it matters most (numeric, neural).

03Adversarial gate & negative controlsStrong

In the engine

gg_adversarial.ring (23,481 lines, 1,416 assertions): its thesis is "every assertion exists because a defect survived a green suite and was found by rendering a picture and looking at it." It carries 58 negative siblings (proving each instrument can fail) and 82 discharges() that generate the plan's status table from the suite.

Measured against

mutation testing (in spirit)approval testing

To complete

Assertions born from real escaped defects, negative controls, and a plan-discharge link — a rigor discipline most suites never reach. Distinctive.

04The unified quality gateStrong

In the engine

stzRuleReport collects findings in one shape [:rule,:subject,:where,:severity,:message] from 13 rule domains (code, security, agent, org, service, and diagram notations), with IsSound(); 14 code rules + the knob gate; and a signable predicate set (stzPredicateSet, sha256-sealed .zrlz).

Measured against

SonarQubesemgrepquality gates

To complete

One gate over code and security and agent and process rules — a unification SonarQube/semgrep (code-only) don't attempt (rated deeper on the Metaprogramming page). Its one weakness: it isn't wired to any CI (lane 12).

05Byte-parity & golden / snapshotSolid

In the engine

plot.zig holds 29 byte-parity tests against ground truth captured from the Haro plotters before the renderer moved (and after three defects were fixed); stzLLMFunction.AddGolden/RunGoldens pins LLM outputs; and the #--&gt; markers capture expected stdout.

Measured against

jest-snapshotapprovaltestsinsta

To complete

Rigorous snapshot testing (captured post-fix, string-exact) — but snapshots pin current behavior, so a wrong-but-stable output can be frozen; the oracle lane (2) is the stronger guard where it applies.

06FuzzingSolid

In the engine

Five UBSan-trap fuzzers on the untrusted-input parsers — fuzz_http, fuzz_tls (X.509), fuzz_pcre2 (300k rounds, ReDoS-bounded), fuzz_sqlite, fuzz_utf8 — wired into zig build fuzz, any UB becoming a hard crash.

Measured against

libFuzzerAFLgo-fuzz

To complete

Real fuzzing of exactly the right targets — but engine-only (5 harnesses), random-round not coverage-guided (no libFuzzer feedback or evolving corpus), and not run continuously.

07Real-process & integration testingSolid

In the engine

The D0–D6 cluster guards spawn genuine OS processes (via uv_spawn), exchange framed STZM messages over loopback, perform real kills to test supervision, and assert clean teardown; the appserver guards run a second reactor as a live client.

Measured against

testcontainersintegration harnesses

To complete

Integration testing against real processes and real failures (not mocks) — rigorous where it exists, but a focused set (cluster / appserver), not a general integration-test framework.

08Engine unit tests (Zig)Solid

In the engine

Inline test &quot;…&quot; blocks in 151 of 371 engine .zig files — the native Zig unit layer under the Haro guards, run by the build's test step.

Measured against

zig testcargo testgo test

To complete

Standard, well-used inline unit testing at the engine layer. Coverage of the 371-file engine is broad but not universal (151 files), and unmeasured (lane 12).

09Stress & scale testingSolid

In the engine

Million-scale guards (1M-item IntSeq builds ~7 ms vs >60 s; 999_*_millions string/list suites) and multilingual stress (Arabic/CJK/emoji through the same paths), catching O(n²) regressions and byte-corruption at scale.

Measured against

perf regression suitesload harnesses

To complete

Scale and multilingual correctness are tested as first-class properties — a real strength — though the timed guards inherit the machine-load sensitivity the perf plane documents.

10Test-as-documentationSolid

In the engine

The narrated guards are designed to double as readable specs, and a parallel prose corpus of 135 narrations (base/doc/narrations) explains the same features the guards prove — a runnable-and-readable pairing.

Measured against

doctestCucumber featuresliterate testing

To complete

A genuine test-as-doc intent — but the guard↔narration link is convention, not enforced: the two can (and once did) diverge, letting a bug hide behind a prettied-up narration.

11Property & mutation testingPartial

In the engine

Three prop_*.zig files — prop_crypto (determinism / tamper-detection plus mutation: "constant + first-byte hashes must be killed"), prop_http, prop_ratebucket (token-bucket invariants).

Measured against

Hypothesis / QuickCheckStryker / PIT

To complete

Engine-only, 3 files. No Haro-side property testing, no generator/shrinking framework (Hypothesis), and no mutation-testing framework for the library — the mutation discipline lives only inside those crypto/http/ratebucket props.

12Coverage, CI & suite healthPartial

In the engine

Coverage is by assertion count (chk / Then / #--&gt; / discharged plan items); the pipeline is bespoke Python runners (_run_test_batch.py, _annotate_test_errors.py, promises.py) plus zig build.

Measured against

pytest-cov / istanbulGitHub ActionsStryker

To complete

No coverage % (no line/branch instrumentation), no CI config (.github absent), and a fidelity-grind backlog: the classic #--&gt; suites sit ~41–60% green with 1,312 #ERR markers, while the curated narrated surface is the green, maintained one.

Ce qui est dû, dans l'ordre du rendement

Les manques, classés par ce qu'ils rapportent et non par leur taille ; la valeur est l'effet sur la portée de la bibliothèque, l'effort une lecture d'ingénieur.

Tier A — make the discipline enforceable

A standard CI pipeline

There is no .github / CI config — the bespoke runners and zig build should run on every push, with the unified rule gate (stzRuleReport) as a required check. The whole point of a quality gate is to gate; today it's a library API nothing runs automatically.

Valeur · élevéeEffort · faible
Coverage instrumentation

Line/branch coverage for the engine (and, where feasible, the Haro guards) so "we assert a lot" becomes "we cover X%." Assertion counts show effort, not reach — the one number this rigorous system cannot currently produce.

Valeur · élevéeEffort · moyen

Tier B — broaden the techniques

Haro-side property testing

A Hypothesis-style generator/shrinking harness for Haro library code — property testing is engine-only (3 files) today. It would fit the library's "assert the mechanism" ethos and find the edge cases example-based guards miss.

Valeur · moyenneEffort · moyen
A shipped assertion module

Retire the copy-pasted per-file chk() for one imported harness (the _narrated.ring DSL is the seed), so every guard shares one tallying, diffing, skip-aware assertion surface instead of 455 near-copies.

Valeur · moyenneEffort · faible
Coverage-guided / continuous fuzzing

Give the five fuzzers libFuzzer-style coverage feedback and an evolving corpus, and run them continuously in CI — turning random-round harnesses into corpus-growing regression fuzzers.

Valeur · moyenneEffort · moyen

Tier C — pay down the debt

Close the fidelity-grind backlog

The classic #--&gt; suites sit ~41–60% green with 1,312 #ERR — mostly output drift and lost shared setup, not real bugs. Reconciling them makes the whole corpus vouch, not just the curated narrated surface.

Valeur · moyenneEffort · élevé
Mutation testing for Haro code

Extend the engine's "these mutations must be killed" discipline (today only in the crypto/http/ratebucket props) into a mutation-testing pass over the library — the strongest measure of whether the many assertions actually catch defects.

Valeur · moyenneEffort · élevé
Enforce the guard↔narration link

Bind each prose narration to the guard that proves it, so the two can't diverge silently (the underscore-vs-space case where a bug hid behind a prettified narration) — turning test-as-doc from convention into contract.

Valeur · faibleEffort · moyen
