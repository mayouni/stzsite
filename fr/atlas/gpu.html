Visuel et spatial

GPU

Calcul et rendu sur un même périphérique, avec une fonderie qui se règle et se vérifie elle-même ; f64 et multi-GPU refusés par choix.

5 Strong · 4 Solid · 3 Partial · 0 Emerging

Mesuré contre : wgpu · taichi · three.js · Dossiers : base/gpu(s'ouvre dans un nouvel onglet) · Le guide des fonctions de ce domaine

Repensé depuis les premiers principes

Ce que Softanza a gardé de ce qui marche, et ce qu'elle a repensé, tel que la bibliothèque l'a écrit dans ses documents de conception et ses narrations.

La manière SoftanzaLe GPU n'est utilisé que là où une mesure prouve qu'il gagne, et le chemin CPU reste toujours la réponse de référence.

Gardé des meilleures pratiques

  • Une seule bibliothèque légère et éprouvée est intégrée : wgpu-native (WebGPU). Les noyaux se compilent depuis du texte à l'exécution, et les mêmes noyaux tournent aussi dans un navigateur. source(s'ouvre dans un nouvel onglet)
  • Les données restent sur la carte : un envoi, plusieurs noyaux enchaînés, une seule relecture, car déplacer les données coûte plus que les traiter. source(s'ouvre dans un nouvel onglet)
  • Chaque opération GPU est livrée avec une vérification de parité contre le résultat CPU, dans une tolérance fixée par la mesure. source(s'ouvre dans un nouvel onglet)

Repensé

  • Le calcul exact en double précision reste sur le CPU : les cartes grand public y sont 32 à 64 fois plus lentes. Le GPU se limite à la simple précision. source(s'ouvre dans un nouvel onglet)
  • Chaque passage au GPU doit gagner une mesure, selon des critères d'abandon écrits d'avance. Les opérations élément par élément isolées ont été écartées : le transfert pesait 92 % du coût. source(s'ouvre dans un nouvel onglet)
  • Le calcul GPU se décrit au lieu de s'écrire. stzKernelMaker change une courte formule en noyau, ce qui le rend abordable, comme le générateur de regex l'a fait pour les motifs. source(s'ouvre dans un nouvel onglet)
  • Les variantes de noyaux viennent d'une simple boucle, et non d'un modèle de langage, car l'espace de recherche est petit. Un vérificateur contrôle chacune et refuse les vitesses impossibles. source(s'ouvre dans un nouvel onglet)

An in-house wgpu plane that does what neither three.js (render-only) nor taichi (compute-only) does: compute and render on one device, zero-copy. Its distinctive core is a self-tuning foundry; real consumers are accelerated and verified (t-SNE 5-8x, UMAP up to 16x, k-means 6x, neural forward 5x, exact vector search 18x), always with a bit-identical CPU fallback. What it refuses by measured decision — f64 on GPU, multi-GPU, deep 3D — are scope boundaries, not oversights.

Ce qu'un artisan en fait, et ce qui se distingue

  • a self-tuning, self-checking calibration foundry: category-of-one
  • compute and render zero-copy on one device
  • every GPU route measured, verified, and reversible to CPU
  • byte-identical WGSL native vs browser

Ce qui est dû

  • broaden the kernel transpiler beyond elementwise
  • whole-pipeline GPU residency
  • idle-aware routing (GK1b)
  • deeper 3D rendering

La manière Softanza, exécutée

Ce que Softanza fait autrement dans ce domaine, montré par du code tiré de ses narrations et de ses gardes, et exécuté pour cette page.

Une formule d'une ligne devient un noyau GPU ; l'écrire ne demande aucun appareil, et le code produit se lit avant toute exécution.

k1.ForEachElement('{ @C = alpha * @A + @B }')

Sortie
struct StzTile { xoff : u32, p0 : u32, p1 : u32, p2 : u32 }
@group(0) @binding(0) var<uniform> tile : StzTile;
struct P { n : u32, pad : u32, s_alpha : f32 }
@group(0) @binding(1) var<uniform> p : P;
@group(0) @binding(2) var<storage, read> v_a : array<f32>;
@group(0) @binding(3) var<storage, read> v_b : array<f32>;
@group(0) @binding(4) var<storage, read_write> v_c : array<f32>;
@compute @workgroup_size(256)
fn main(@builtin(global_invocation_id) gid : vec3<u32>) {
  let i = gid.x + tile.xoff * 256u;
  if (i < p.n) { v_c[i] = p.s_alpha * v_a[i] + v_b[i]; }
}
