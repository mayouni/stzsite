stzPerfMonitor

30 own methods · 3 forms written with extensions, listed under their method

the source: base/perf/stzPerfMonitor.ring(opens in a new tab) · All classes · The area reference: Performance

The program's own instrument panel: it watches memory and processor, keeps the metrics you declare, records request traces, and writes them out in the formats the monitoring world reads, while measuring what the watching itself costs.

What to watch is declared, memory, processor, system memory, at a given cadence, and so are the program's own metrics, counters, gauges and timers, or the labelled forms that give one family a child per route or per method.

o1 = new stzPerfMonitor("shop")
o1 {
    NewCounter("orders")
    NewTimer("checkout.ms")
}

? o1.NumberOfMetrics()
#--> 2

? @@( o1.Metrics() )
#--> [ [ "orders", "counter" ], [ "checkout.ms", "timer" ] ]
run in the library on 2026-10-19

Sampling can be called from any loop, and it only samples when the cadence has elapsed on the monotonic clock; or it runs standalone for a while; or it is hosted by an agent host, so that a server ticks a monitor between requests. The last requests are kept as traces in an engine ring, each with its id, path, status and durations.

Every metric is exported as Prometheus text or as an OpenTelemetry batch, or explained in words. And the monitor reports what the observation itself used, with the same clock, so that the profiler is profiled. It serves a service with a latency promise, a batch that must stay inside its memory, a test that asserts a budget, and the well-known subjects that the server's request bracket feeds.
