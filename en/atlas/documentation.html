Documentation system

Docs are run, not written; the library documents itself queryably; plans record what shipped; no site, no generated reference.

3 Strong 6 Solid 2 Partial 1 Emerging

Measured against: Sphinx · rustdoc · MkDocs · literate programming · Folders: base/doc(opens in a new tab) · base/meta(opens in a new tab) · base/reflect(opens in a new tab) · For programmers: this area's reference

Documentation in Softanza is run, not just written: every example shows real output, and the library can explain itself from its own source.

The corpus is 134 narrations that teach an idea as a story in which every code block and every output block came from an executed demo and is pinned by a guard; 22 quick starts and a tree of recipes for the reader in a hurry; eight deep dives and the design studies for the engineer who wants the why; and some sixty plans of record written before the code, then amended as each phase closed, so a design document records what shipped rather than what was intended. A course chapter stores no output: each cell promises what it prints, all cells run in a fresh process, and a wrong promise is caught.

The library documents itself. Asked how to remove duplicates from a list, it composes the method name from the naming grammar and says it did; explaining a method answers from the source comment, and refuses a method that does not exist instead of inventing one; no language model is involved, because the knowledge already lives in the source. The figures in the documents are drawn by the thing being documented. This website is the delivery those files lacked: every reference page here is harvested from those comments, and every example on it was run.

Where it stands

The Compass's sentences are in English, as it wrote them.

Documentation is not a module in Softanza — it's a discipline built into how the library is made, and its signature is that the docs are run, not written, and the library can document itself. 134 literate narrations teach a concept through a story whose every code-and-output block is produced by a real executed demo and pinned by a narrated guard; the library answers Ask() / HowTo() / ExplainMethod() about its own API — harvested from source, deterministic and zero-hallucination; 2,956 files carry inline #--&gt; promises a harness checks against real output; and ~63 plans-of-record record what actually shipped, not just what was intended. Where it's thin: there is no published doc site, no generated API reference, and no measured coverage — the corpus is markdown-on-GitHub by design, and its own overview has drifted behind the system it describes.

The honesty line on the ratings. This page rates a cross-cutting system, not a module — there is no base/doc-engine; it is a corpus (134 narrations, ~63 plans, 22 quickers, 8 deepdives) plus two shipped mechanisms (self-doc Ask/HowTo; the #--&gt; promise harness) and a source-harvesting doc-comment convention. Read from main. The strengths are real and largely without peer — run-verified narrations, a library that answers questions about itself deterministically, design docs that record outcomes. The weaknesses are delivery-level and honestly visible in the repo: no site, no generated reference, no coverage number, and an overview that has drifted behind its own system. The split is the story: the authoring is ahead of the field; the publishing is behind it.

The one-sentence position. Softanza documents the way it builds — narrations that run, a library that explains itself, plans that record what shipped — an authoring discipline more rigorous than most doc toolchains produce; what it lacks is the ordinary delivery those toolchains ship for free: a published, searchable site, a generated API reference, and a coverage number.

Rethought from first principles

What Softanza kept from what works, and what it rethought, as the library wrote it down in its design documents and narrations.

The Softanza wayDocumentation is run, not just written: every example shows real output, and the library can explain itself from its own source.

Kept from the best practice

  • Several doors for several readers: one-liners for the hurried, narrations for story lovers, references for structured lookup, deep dives for engineers, and FAQs. source(opens in a new tab)
  • Plain markdown files kept with the code and hosted on GitHub, so the documentation stays lightweight and accessible. source(opens in a new tab)
  • Each method is described where it lives, in a comment in the source, and section headers group methods by capability. source(opens in a new tab)

Rethought

  • Narrations explain an idea as a story with real code. Every output block is the actual output of a run, and a guard keeps it true. source(opens in a new tab)
  • A chapter stores no output. Each cell promises what it prints, all cells run in a fresh process, and a wrong promise is caught, not hidden. source(opens in a new tab)
  • Ask the library in plain words and it answers from its own source comments, with no large language model, because the knowledge already lives there. source(opens in a new tab)
  • Because method names follow a grammar, HowTo composes a name from your intent and checks it against the real methods, falling back to search by meaning. source(opens in a new tab)

12 lanes, each against the best of its category

For every lane: what runs in the engine today, the tools it is fair to measure it against, and what is still owed.

01Run-verified literate narrationsStrong

In the engine

134 narrations (base/doc/narrations) teach a concept as a story where every code and output block is real and executed — each paired with a runnable *_narration_demo.ring (17) that produces the pasted output and a *_narrated.ring guard (455) that pins the behavior forever. The pledge is explicit: "the run lives in … the guard suite is …".

Measured against

literate programming (Knuth)Jupyterorg-mode Babel

To complete

A distinctive standard. Two warts: the demo→guard pledge is textually cited in only ~27 of 134 narrations, and the output blocks are hand-pasted — a demo edit can silently diverge from the essay (only the guard, where present, catches behavior drift).

02Self-documenting, queryable libraryStrong

In the engine

stzSelfDoc / stzLibDoc answer Ask(), HowTo(intent), ExplainMethod(), BestMethodFor() — harvesting methods and doc-comments from source, ranking with a lexical-IDF retriever (19/30 vs a reranker's 15 on its own benchmark) and a neural rescue tier only when lexical finds nothing. Deterministic, zero-hallucination: every answer is a real method of the class.

Measured against

help() / pydocrustdoc search(no direct peer)

To complete

No competitor in the field does this. HowTo even composes a method name from the intent and grounds it against the real API. Weakness: the default stzLibDoc corpus is only 2 curated classes — you must pass your own list to widen it.

03Plans-of-record with resultsStrong

In the engine

~63 design docs (44 in base/doc/design + ~19 SOFTANZA_*_PLAN.md beside the modules) written before the code, then amended as phases close: SOFTANZA_PERF_SYSTEM.md opens Status: COMPLETE — P0-P11 ALL SHIPPED and records, per phase, the exact files, the guard count, and the narration written for it — the "house triple" (design + guard + narration).

Measured against

ADRsRFCsdesign docs

To complete

Design docs that record outcomes, not just intent. Most projects' design docs rot the day the code lands; here the STATUS/RESULTS banners keep the design/ tree the most actively maintained surface in the system.

04Docs-as-tests (the promise harness)Solid

In the engine

2,956 files carry inline promises — ? expr #--&gt; result — and base/meta/promises.py runs each file, captures stdout, and walks the promises as an ordered subsequence (tolerant of banners), canonicalizing list whitespace and recognizing PROSE notes (but should, currently) as documentation-debt rather than expectations.

Measured against

rustdoc doctestspython doctestElixir doctest

To complete

A real doctest layer over the whole corpus — but it's a standalone runner, not wired into CI, and the same corpus knowingly tolerates stale promises (recorded bugs since fixed), so a green run and a current corpus are two different claims.

05Doc-comments harvested from sourceSolid

In the engine

The harvester in stzReflectFuncs.ring reads a doc-comment block above each def — and does more than copy it: boxed #==# section headers become a coarse meaning that lifts undocumented methods, variants inherit their documented base's description, and it synthesizes signatures from the def line plus the CheckParam block.

Measured against

docstringsJSDocrustdoc comments

To complete

A genuine, source-of-truth doc-comment convention with clever fallbacks — but description quality is uneven where source is thinly commented, and nothing emits those harvested comments as a browsable manual (lane 10).

06Audience-layered taxonomySolid

In the engine

Docs are sorted by reader and intent: quickers (22 + recipes/) for the hurried, narrations (134) for learners, deepdives (8) for the curious, references for lookup, faqs for troubleshooting, internals (5) for contributors — a split that maps cleanly onto the Diátaxis quadrants.

Measured against

DiátaxisDivio doc system

To complete

The right shape, deliberately chosen — but unevenly filled: references/ holds only 3 files and faqs/ just 1, and a misc/ catch-all (9) sits outside the taxonomy.

07Quick-starts & recipesSolid

In the engine

22 quickers plus a recipes/ tree (list / number / string / text) give fast, copy-ready one-liners and step-by-step guides — the "programmer in a hurry" path — and the recipes are also ingested as retrieval entries by the self-doc index.

Measured against

cookbook docsgetting-started guides

To complete

A solid task-oriented layer that feeds two systems at once (humans and the self-doc retriever). Coverage is breadth-limited to the core data types rather than the whole library.

08Conceptual & deep-dive essaysSolid

In the engine

8 deepdives plus reflective design studies (SCOPE_ORIENTED_PROGRAMMING.md, SOFTANZA_ENGINE_ARCHITECTURE.md, the *_VS_THE_FIELD.md comparatives) carry the why — paradigm, architecture and critique — the explanation quadrant most libraries never write down.

Measured against

To complete

Real explanatory depth — a differentiator over reference-only doc sets. It's essay-driven and author-voiced rather than systematically indexed, so discovery relies on knowing the file exists.

09Self-illustrating figuresSolid

In the engine

The library draws its own documentation figures: the graphics plane (stzCanvas, stzGraphCanvas, stzPlotCanvas, stzTreeCanvas) exports the charts, graphs and org-charts embedded in the docs — narrations/images holds library-rendered exports (graphviz/mermaid, natural-language and Ajami samples).

Measured against

To complete

Figures produced by the thing being documented — self-proving in a way a hand-drawn diagram never is. But they are committed PNGs: nothing regenerates them on a doc build, so a figure can age past the code that made it.

10Browsable API referencePartial

In the engine

The "reference" is the queryable self-doc computed live (lane 2), which sees every harvested method — plus a hand-written references/ directory of 3 files. There is no static, browsable, cross-linked API manual.

Measured against

Sphinx autodocrustdoc HTMLDoxygen

To complete

No API-reference generator. The harvester already reads every method and signature — emitting that as browsable HTML is the missing last step. Today API discovery means running a query or reading source, not opening a page.

11Doc health & coveragePartial

In the engine

Freshness is held by the plans-of-record discipline (lane 3) and, for runnable claims, by the promise harness (lane 4) and narrated guards. What exists is behavioral freshness for the parts that run.

Measured against

doc coverage toolsVale / docs lintersinterrogate

To complete

No measured doc coverage — no "% of methods with a real doc-comment," and prose freshness is unenforced: the system's own stz-doc-system-overview.md still describes 5 pillars while the tree has 9 surfaces, omitting design/, internals/ and the entire self-doc system.

12Published site & discoverabilityEmerging

In the engine

The whole corpus is hand-written markdown read on GitHub — the overview names this explicitly and lists "interactive code, smart search, video" as future work. No mkdocs.yml, conf.py, docusaurus.config.js or .rst exists anywhere in the tree.

Measured against

Read the DocsDocusaurusMintlify

To complete

No published doc site, no search, no versioned rendering. The richest authoring system in the field is delivered as a folder of files — discoverability depends on browsing the repo. This is the single largest gap between what the docs are and how they reach a reader.

What is owed, in the order of return

The gaps, ordered by what they bring and not by their size; value is the effect on the library's reach, effort an engineer's reading.

Tier A — get the docs to a reader

A published doc site

Point a static-site generator (MkDocs / Docusaurus) at the existing markdown — the content is already written, taxonomized and figure-rich. This turns a folder browsed on GitHub into a searchable, navigable site, closing the one gap (lane 12) that keeps the best-authored corpus in the field hard to reach.

Value · highEffort · low
Generate the API reference

The stzReflectFuncs harvester already reads every method, signature and doc-comment. Emit it as browsable HTML — a rustdoc/Sphinx-class reference the library can produce about itself, with no separate doc-comment pass required (lane 10).

Value · highEffort · medium

Tier B — close the cheap drift

Refresh the system overview

stz-doc-system-overview.md still describes 5 pillars for a 9-surface system, omitting design/, internals/ and self-doc entirely. Rewriting the map of the docs is a day's work and the first thing a new reader hits.

Value · mediumEffort · low
Widen the self-doc corpus

stzLibDoc curates only 2 classes by default. Expanding the default index across the core types makes Ask() answer for the whole library out of the box, not just when a caller passes their own class list.

Value · mediumEffort · low
Regenerate narration outputs

Have the *_narration_demo.ring runs re-emit the output blocks pasted into each narration, so a demo edit can't silently diverge from the essay — turning the "every block is run" pledge from convention into a build step (lane 1).

Value · mediumEffort · medium

Tier C — measure & enforce

Measured doc coverage

Report the share of public methods carrying a real doc-comment (vs. relying on section/sibling fallbacks), so "the library documents itself" gains a number. The harvester already knows every method — the denominator is free (lane 11).

Value · mediumEffort · medium
Wire docs into CI

Run promises.py and the narrated guards on every push so a doc code-block that stops matching its output fails the build — the doctest and literate layers already exist; nothing runs them automatically (lanes 1, 4).

Value · mediumEffort · medium
Fill the thin quadrants

Populate references/ (3 files) and faqs/ (1) so the deliberately-chosen taxonomy is evenly stocked — the reference quadrant, in particular, is what the API generator above would largely fill for free (lane 6).

Value · lowEffort · high
