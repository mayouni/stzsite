Rethought from first principles

What Softanza kept from what works, and what it rethought, as the library wrote it down in its design documents and narrations.

The Softanza wayDocumentation is run, not just written: every example shows real output, and the library can explain itself from its own source.

Kept from the best practice

  • Several doors for several readers: one-liners for the hurried, narrations for story lovers, references for structured lookup, deep dives for engineers, and FAQs. source(opens in a new tab)
  • Plain markdown files kept with the code and hosted on GitHub, so the documentation stays lightweight and accessible. source(opens in a new tab)
  • Each method is described where it lives, in a comment in the source, and section headers group methods by capability. source(opens in a new tab)

Rethought

  • Narrations explain an idea as a story with real code. Every output block is the actual output of a run, and a guard keeps it true. source(opens in a new tab)
  • A chapter stores no output. Each cell promises what it prints, all cells run in a fresh process, and a wrong promise is caught, not hidden. source(opens in a new tab)
  • Ask the library in plain words and it answers from its own source comments, with no large language model, because the knowledge already lives there. source(opens in a new tab)
  • Because method names follow a grammar, HowTo composes a name from your intent and checks it against the real methods, falling back to search by meaning. source(opens in a new tab)

Documentation is not a module in Softanza; it is a discipline built into how the library is made, and its signature is that the docs are run, not written, and the library can document itself. 134 literate narrations teach through stories whose every code-and-output block is produced by a real executed demo; the library answers Ask() / HowTo() / ExplainMethod() about its own API deterministically; 2,956 files carry inline #--> promises a harness checks; ~63 plans-of-record record what actually shipped. Where it is thin: no published doc site, no generated API reference, no measured coverage, and its own overview has drifted behind the system it describes.

What a crafter does with it, and what stands out

  • The docs are run, not written: 134 narrations whose every block is produced by an executed demo
  • The library documents itself: Ask() / HowTo() / ExplainMethod() are deterministic and zero-hallucination
  • Design docs that record what actually shipped, not just what was intended
  • Self-illustrating figures drawn by the thing being documented

What is owed

  • A published doc site (MkDocs / Docusaurus over the existing markdown)
  • Generate the API reference from the stzReflectFuncs harvester
  • Refresh the system overview (5 pillars vs 9 surfaces) and widen the self-doc corpus beyond 2 classes
  • Measured doc coverage, and docs wired into CI
