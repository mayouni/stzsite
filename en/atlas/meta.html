Metaprogramming & code rules

One CI gate over about eleven domains, a unification no peer has; trails on declarative rule authoring.

1 Strong 7 Solid 4 Partial

Measured against: semgrep · OPA · Folders: base/meta(opens in a new tab) · base/reflect(opens in a new tab) · base/refine(opens in a new tab) · base/governance(opens in a new tab) · For programmers: this area's reference

Where it stands

The Softanza Compass's reading: every lane of the area rated against the best of its category, by what the guards prove. Read from the source on 2026-09-16, from a read-only main worktree. The Compass's sentences are in English, as it wrote them.

The distinctive thing here is unification, not any single tool. One CI gate (stzRuleReport) collects findings in one shape from ~11 domains — code rules, agent-graph invariants, security reachability, org charts, service contracts, workflow SLAs, even diagram notations — something neither semgrep (code-only) nor OPA (policy-only) attempts. Around it sits a broad band of Haro-side meta tools: a graph+text code-rule engine whose rules were born from the library's own hard-won bugs (so it lints itself), a three-language code graph, a governance contract model, a deterministic self-documentation surface, and a signable rule constitution. The honest gaps are extensibility (no way to author a custom rule pattern), a two-grammar tree-sitter, and shallow reflection.

The honesty line on the ratings. Re-surveyed from main. Mostly Haro (only tree-sitter parse, the governance clock, and the optional neural tier are engine-backed). Guards prove the substance: the code graph is structural, not prose (ownership/ancestry/impact), the rules avoid the text-scanner false positives (a def substr( or a comment "def len" isn't flagged), and MayProceed composition + lineage completeness hold. Two memory corrections verified: the knob gate is now nine passes / 14 rules (not "six"), and the DRIFT the memory warns of is structurally prevented by a single-source list; the "perf/plastic" domains from memory are not wired as report subjects (the real subjects are the ~11 above). Tree-sitter / Python-ast scenarios skip cleanly when the DLL isn't built — no #ERR.

The one-sentence position. Softanza's meta plane wins on a unification no competitor offers — one gate, one finding shape, across code, security, agents, processes and diagrams — and trails on the thing they're built for: letting a user author a new rule or policy declaratively, over a deeper code model and richer reflection than it currently exposes.

What a crafter does with it, and what stands out

  • One CI gate, one finding shape, across ~11 domains -- a genuine category-of-one
  • Code rules born from the library's own hard-won bugs, so it lints itself
  • A three-language code graph (Haro, Python, JS) that self-checks via CheckRules()
  • A signable, sha256-sealed rule constitution -- governance of the rules

What is owed

  • Declarative rule and policy authoring (semgrep-style patterns, Rego-style expressions)
  • Broaden tree-sitter and put Haro on it
  • Richer reflection; resolved call edges and dataflow; full dominator analysis for effects-guarded
  • Production-harden the semantic resolver; a policy expression language

Rethought from first principles

What Softanza kept from what works, and what it rethought, as the library wrote it down in its design documents and narrations.

The Softanza wayA house rule is not folklore or a text pattern: it is an object checked over a model of the code, runnable by any programmer, human or machine.

Kept from the best practice

  • Findings carry a severity: errors fail the build, warnings only advise. Existing checkers keep their old output shapes behind thin adapters, so nothing downstream breaks. source(opens in a new tab)
  • Not everything belongs on a graph. A naming rule such as no-aggressive-verbs stays a plain text check; the aim is to stop pretending a text scan is a model. source(opens in a new tab)
  • Rules that change behaviour roll out gently: constraint rules ship opt-in per domain, in validation mode first, with a migration window for existing callers. source(opens in a new tab)

Rethought

  • Rules run over a code graph, not line by line. The graph tells a definition from a call and sees two methods colliding by case, which a line scan cannot. source(opens in a new tab)
  • Guardrails become gates, not audits. A constraint rule refuses illegal wiring when it is built: granting an effect capability to a language-model actor is rejected on the spot. source(opens in a new tab)
  • One rule engine serves code, agents, security, workflows and org charts, with one finding shape and one gate. Performance budgets and data findings join the same gate. source(opens in a new tab)
  • Thousands of test lines state the output they promise. A harness runs each file and compares, and is itself tested on deliberately wrong promises. source(opens in a new tab)

12 lanes, each against the best of its category

For every lane: what runs in the engine today, the tools it is fair to measure it against, and what is still owed.

01The unified rule report (one CI gate)Strong

In the engine

stzRuleReport collects findings in one shape — [:rule,:subject,:where,:severity,:message] — from any graph that answers CheckRules(), across ~11 domains: code, agentic, security, org-chart, service, workflow SLA, fault-tree, ER, network, Petri, family. IsSound() = zero errors; legacy checkers normalize in via IngestLegacy.

Measured against

semgrep (code-only)OPA (policy-only)SonarQube

To complete

No peer unifies code rules, security reachability, agent invariants, process SLAs and diagram correctness into one gate with one finding shape. A genuine category-of-one.

02Governance / policy modelSolid

In the engine

stzGovernance — policy as data (.zgov): risk tiers 1–4, permission (CAN) vs authority (SHOULD) composed by MayProceed (undeclared → refused, every verdict narrated), commitment state, decommission obligations, decision lineage, reversibility classes and trust postures.

Measured against

OPA / RegoXACMLAWS IAM

To complete

Richer primitives than OPA (lineage, reversibility, postures) — but a fixed-primitive data model, not a query language: you declare data, you can't write arbitrary Rego-style policy logic (lane 12).

03Code-rule engineSolid

In the engine

A hybrid engine: graph-query rules over a code graph plus statement text-passes — 14 named rules incl. no-len-method, engine-first, no-case-collision, writes-a-mutable-constant (the NL/TRUE/FALSE clobbering guard), no-dead-code. Graph-awareness avoids the false positives a text scanner makes (a def substr( isn't flagged).

Measured against

semgrepESLintruff

To complete

Real, self-applied rules born from the library's own bugs — but a house-specific catalogue, not a general AST-pattern engine: you can't write $X.foo()-style matchers the way semgrep lets you.

04Code as a graphSolid

In the engine

stzCodeGraph across three languages (Haro source-truth parser, Python, JS): classes / methods / calls / inheritance, with queries Ancestry, Subclasses, Impact, Cascade, Callers/Callees, DeadCode, CyclicCalls — and it self-checks via CheckRules().

Measured against

Sourcetrail / Understandsemgrep dataflowstack-graphs

To complete

Call resolution is name-based — honest about dynamic dispatch ("candidates, not proof"), so DeadCode/CyclicCalls are approximate. No dataflow / taint (the semgrep-pro axis, lane 12).

05Knob gate (library hygiene)Solid

In the engine

StzCheckProjectKnobs — nine text-passes over the tree (dead-knob, library-prints, empty-method-body, writes-a-mutable-constant, value-called-as-function, for-in-loops…), all from a single source list so entry points can't drift (the past drift bug is structurally prevented).

Measured against

ruff / ESLint custom rulesclippy

To complete

A real library-wide hygiene gate catching Haro-specific footguns most linters can't express — but narrow to those known footguns, and text-pass (so the deeper structural checks live in the graph engine).

06Self-documentation (Ask / ExplainMethod)Solid

In the engine

stzSelfDoc / stzLibDoc: Ask a class what it can do (lexical IDF first, neural embedding/reranker rescue only on zero overlap), ExplainMethod (deterministic templated), HowTo (grammar-compose a method name, then retrieve) — harvested from source, "zero hallucination."

Measured against

docstrings + SphinxAI code assistants

To complete

A distinctive self-querying library (real methods, not hallucinations) — but coverage depends on doc-comment harvest, and the retrieval floor is lexical; a prototype-grade surface, not a full doc system.

07Code refinementSolid

In the engine

stzRefinableCode: typed refinement points (&lt;R:PARAM|ALGO|LIB …&gt;) with a five-stage gate (structural → constraint → governance → trust posture → cross-point derivation) and a reversibility timeline (RevertTo/Redo/checkpoints), format .zrfn.

Measured against

template / codegen toolsrefactoring engines

To complete

A governed, reversible refinement-points mechanism — but niche: it tunes declared knobs under predicates, it is not general code generation or automated refactoring.

08Signable rule constitutionSolid

In the engine

stzPredicateSet: assemble rules (AddRule from the code-rule names) and invariants into a constitution, Save/LoadFrom/Verify/EnforceOnCode, sealed with sha256 (.zrlz).

Measured against

OPA bundlespolicy-as-code signingsigstore policy

To complete

A verifiable, tamper-sealed rule set — governance of the rules — but built from the fixed rule/invariant catalogue, so its reach grows only as the catalogue does.

09Reflection / introspectionPartial

In the engine

Runtime discovery on stzObject: Methods(), Attributes(), AttributesAndValues(), Type(), ClassName() — over Haro's own builtins.

Measured against

Python inspectJava reflectionRuby / Smalltalk

To complete

Shallow: names and values, but no signatures / parameters / decorators / annotations and no dynamic-invocation surface beyond a plain call — below Python's inspect or Java reflection.

10Tree-sitter polyglotPartial

In the engine

Vendored tree-sitter runtime compiled from source (tree_sitter.zig) with a walk() that maps CST nodes to a shared CLASS|/METHOD|/CALL| protocol — and "add a language = grammar + walk()" is real, documented in-engine.

Measured against

tree-sitter (dozens of grammars)semgrep parsers

To complete

Only two grammars (Python + JavaScript), parse-only (no tree-sitter queries or transforms exposed), and Haro itself isn't on it (its own parser). The extension path exists; the breadth doesn't yet.

11Semantic resolver (one lexicon)Partial

In the engine

stzSemanticResolver merges three lexical sources into one semantic-ID-keyed lexicon (StzResolveSemantic), lexical IDF first with a neural embedding rescue when a model is loaded — the library's "one lexicon" for near-natural coding.

Measured against

intent resolution / NLUsynonym/ontology stores

To complete

Described in source as "the unification prototype" — the mechanism works, but it is early: coverage, growth and cross-domain consistency are not yet production-hardened.

12Custom rule / policy authoringPartial

In the engine

Extending the system means writing a Haro stzGraphRule checker or a governance declaration — programmatic, not declarative.

Measured against

semgrep patterns (YAML)OPA / RegoESLint plugins

To complete

No declarative authoring surface: you can't write a semgrep-style AST pattern or a Rego-style policy expression without hand-coding a checker. This is the extensibility both category leaders are built on.

What is owed, in the order of return

The gaps, ordered by what they bring and not by their size; value is the effect on the library's reach, effort an engineer's reading.

Tier A — the extensibility semgrep and OPA are built on

Declarative rule & policy authoring

A way to write a new code rule as an AST/graph pattern (semgrep-style) and a governance policy as an expression (Rego-style) without hand-coding a Haro checker. It turns a fixed catalogue into an open one and is the single biggest lever against both leaders.

Value · highEffort · high
Broaden tree-sitter — and put Haro on it

Vendor more grammars (the whole point of tree-sitter), expose its queries/transforms, and parse Haro itself through tree-sitter so the code graph is one path instead of a bespoke Haro parser plus the polyglot layer.

Value · highEffort · medium

Tier B — deepen the model

Richer reflection

Method signatures/parameters, annotations/decorators, and a dynamic-invocation surface — lifting introspection from names-and-values toward Python inspect / Java reflection, which the self-doc and rule layers would both draw on.

Value · mediumEffort · medium
Resolved call edges + dataflow

Move call resolution beyond name-based candidates so DeadCode / CyclicCalls are proof, and add basic dataflow/taint — the analysis depth that separates a graph from semgrep-pro.

Value · mediumEffort · high
Full dominator analysis for effects-guarded

The source names it as "the next strengthening": prove every input→effect path crosses a guardian (dominator form), not just direct-guard edges — hardening the agent/security invariants the gate already runs.

Value · mediumEffort · medium

Tier C — mature the prototypes

Production-harden the semantic resolver

Take the "unification prototype" to production: measured coverage, disciplined growth, and cross-domain lexicon consistency — the backbone the near-natural surfaces across the whole library lean on.

Value · mediumEffort · medium
A policy expression language

A Rego-class expression layer over the governance primitives, so arbitrary CAN/SHOULD/risk logic can be authored as data rather than composed only from the fixed contracts.

Value · mediumEffort · high
Grow the rule & hygiene catalogue

More code rules and knob-gate passes as new footguns are found — with the single-source discipline that already prevents entry-point drift, so the one gate keeps widening without duplicating lists.

Value · lowEffort · low
