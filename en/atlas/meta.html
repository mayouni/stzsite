Rethought from first principles

What Softanza kept from what works, and what it rethought, as the library wrote it down in its design documents and narrations.

The Softanza wayA house rule is not folklore or a text pattern: it is an object checked over a model of the code, runnable by any programmer, human or machine.

Kept from the best practice

  • Findings carry a severity: errors fail the build, warnings only advise. Existing checkers keep their old output shapes behind thin adapters, so nothing downstream breaks. source
  • Not everything belongs on a graph. A naming rule such as no-aggressive-verbs stays a plain text check; the aim is to stop pretending a text scan is a model. source
  • Rules that change behaviour roll out gently: constraint rules ship opt-in per domain, in validation mode first, with a migration window for existing callers. source

Rethought

  • Rules run over a code graph, not line by line. The graph tells a definition from a call and sees two methods colliding by case, which a line scan cannot. source
  • Guardrails become gates, not audits. A constraint rule refuses illegal wiring when it is built: granting an effect capability to a language-model actor is rejected on the spot. source
  • One rule engine serves code, agents, security, workflows and org charts, with one finding shape and one gate. Performance budgets and data findings join the same gate. source
  • Thousands of test lines state the output they promise. A harness runs each file and compares, and is itself tested on deliberately wrong promises. source

The distinctive thing here is unification, not any single tool: one CI gate (stzRuleReport) collects findings in one shape from ~11 domains -- code rules, agent-graph invariants, security reachability, org charts, service contracts, workflow SLAs, even diagram notations -- something neither semgrep (code-only) nor OPA (policy-only) attempts. The honest gaps are extensibility (no way to author a custom rule pattern), a two-grammar tree-sitter, and shallow reflection.

What a maker does with it, and what stands out

  • One CI gate, one finding shape, across ~11 domains -- a genuine category-of-one
  • Code rules born from the library's own hard-won bugs, so it lints itself
  • A three-language code graph (Haro, Python, JS) that self-checks via CheckRules()
  • A signable, sha256-sealed rule constitution -- governance of the rules

What is owed

  • Declarative rule and policy authoring (semgrep-style patterns, Rego-style expressions)
  • Broaden tree-sitter and put Haro on it
  • Richer reflection; resolved call edges and dataflow; full dominator analysis for effects-guarded
  • Production-harden the semantic resolver; a policy expression language

The Softanza way, run

What Softanza does differently in this area, shown by code taken from its narrations and guards, and run for this page.

The rule reads call edges, so a real call is flagged while a method merely named substr is not.

Softanza
aF = StzCheckCode("class Foo" + nl + "def Bar()" + nl + "	x = substr(s, 2)" + nl)
nF = len(aF)
for i = 1 to nF
    ? aF[i][:rule] + "  @line " + aF[i][:line] + "  [" + aF[i][:severity] + "]"
next
? "findings: " + len(StzCheckCode("class Foo" + nl + "def substr(x)" + nl + "	return x" + nl))
Output
engine-first  @line 3  [warning]
findings: 0

The lanes, one by one

Lanes and their notes are quoted as they were read at the source, on Read from the source on 2026-09-16, from a read-only main worktree.

The unified rule report (one CI gate)
Strong
stzRuleReport collects findings in one shape [:rule,:subject,:where,:severity,:message] from ~11 domains; IsSound() = zero errors; IngestLegacy for old checks.base/graph/stzRuleReport
Governance / policy model
Solid
Policy as data (.zgov): risk tiers, CAN vs SHOULD composed by MayProceed, decision lineage, reversibility, postures; fixed primitives, not a query language.stzGovernance, stzGovernanceChecks
Code-rule engine
Solid
Hybrid graph-query plus text-pass engine, 14 rules born from the library's own bugs; graph-awareness avoids text-scanner false positives; a house catalogue.stzCodeRule, stzCodeRules
Code as a graph
Solid
stzCodeGraph across Haro, Python, JS: Ancestry, Subclasses, Impact, Cascade, Callers/Callees, DeadCode, CyclicCalls; name-based call resolution, no dataflow.stzCodeGraph; CheckRules()
Knob gate (library hygiene)
Solid
StzCheckProjectKnobs: nine text-passes over the tree from a single source list so entry points cannot drift; narrow to known Haro footguns.StzCheckProjectKnobs
Self-documentation (Ask / ExplainMethod)
Solid
stzSelfDoc/stzLibDoc: Ask (lexical IDF first, neural rescue on zero overlap), ExplainMethod (deterministic), HowTo, harvested from source; prototype-grade.stzSelfDoc, stzLibDoc
Code refinement
Solid
stzRefinableCode: typed refinement points with a five-stage gate and a reversibility timeline (RevertTo/Redo/checkpoints, .zrfn); niche, not general codegen.stzRefinableCode
Signable rule constitution
Solid
stzPredicateSet assembles rules and invariants, Save/LoadFrom/Verify/EnforceOnCode, sealed with sha256 (.zrlz); reach grows only with the catalogue.stzPredicateSet
Reflection / introspection
Partial
Methods(), Attributes(), AttributesAndValues(), Type(), ClassName() on stzObject; no signatures, parameters, decorators or dynamic invocation.stzObject
Tree-sitter polyglot
Partial
Vendored tree-sitter with a walk() mapping CST nodes to CLASS|/METHOD|/CALL|; only two grammars (Python, JS), parse-only, Haro itself not on it.tree_sitter.zig
Semantic resolver (one lexicon)
Partial
stzSemanticResolver merges three lexical sources into one semantic-ID-keyed lexicon (StzResolveSemantic); described in source as 'the unification prototype'.base/natural/stzSemanticResolver
Custom rule / policy authoring
Partial
Extending means writing a Haro stzGraphRule checker or a governance declaration; no declarative semgrep-style pattern or Rego-style policy surface.stzGraphRule
