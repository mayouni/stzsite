Web & app server

A competent HTTP server with a built-in SLA, auth and identity provider, and a fake-refusing service-virtualization plane.

4 Strong · 5 Solid · 2 Partial · 1 Emerging

Measured against: Express · FastAPI · WireMock · Folders: base/appserver(opens in a new tab) · base/service(opens in a new tab) · The guide to this area's functions

Rethought from first principles

What Softanza kept from what works, and what it rethought, as the library wrote it down in its design documents and narrations.

The Softanza wayThe server is a host, not a per-request library: the engine is already loaded and warm, and the server only moves requests onto it and results back.

Kept from the best practice

  • Routing stays plain: a table of method, path and handler, with path parameters like /user/:id and a trailing wildcard. Exact routes are tried first. source(opens in a new tab)
  • Login uses published standards: OpenID Connect, passkeys, SAML and one-time codes. A session's token is replaced whenever it gains privilege, which defeats session fixation. source(opens in a new tab)
  • A data back-end is plain REST over the embedded SQLite database: Expose(db, table) gives list, read, create, update and delete, safe from injection, with honest 404s. source(opens in a new tab)

Rethought

  • The engine is resident, so there are no cold starts and no clustering for warmth. Workers scale only for concurrency and load isolation, specialised by competence, not by module. source(opens in a new tab)
  • One host, four shapes: web routes, a data back-end, raw device streams, and hosted agents. Agents share the server's own event loop instead of a separate runtime. source(opens in a new tab)
  • A login does not set a flag or return a role string. It returns an actor carrying capabilities and a trust level, which the rest of the program already understands. source(opens in a new tab)
  • Code the whole app against faithful sandboxes, then switch to real services at deploy. The registry refuses to let a sandbox ship to production. source(opens in a new tab)

Two things live here, and the distinctive one isn't the web server. The HTTP server is real and competent -- reactor-driven HTTP/1.1, Express-like routing, built-in HTTPS/mTLS, auto-CRUD sqlite, and ahead of Express and FastAPI a built-in per-request SLA bracket plus an auth router that is also an OIDC provider -- but middleware is registered-but-never-invoked, with no JSON body parsing, streaming or WebSocket. The standout is the service-virtualization plane: stateful doubles under a governance gate where Deploy(:Production) structurally refuses a fake dependency, even for a fully-entitled human.

What a crafter does with it, and what stands out

  • A built-in per-request SLA bracket with Prometheus /metrics and distributed tracing, ahead of Express and FastAPI
  • A mounted auth router that is also an OIDC provider (discovery, JWKS, authorize, PKCE token)
  • Stateful service doubles that enforce the real service's rules -- WireMock-and-beyond
  • Deploy(:Production) structurally refuses a fake dependency, even for a fully-entitled human

What is owed

  • Execute the middleware pipeline (registered but never invoked)
  • JSON request bodies and streaming responses
  • Serve static files; WebSocket serving; latency injection and a status-aware live adapter in the sandbox
  • OpenAPI/schema and content negotiation; server-side HTTP/2; deeper MBaaS

The Softanza way, run

What Softanza does differently in this area, shown by code taken from its narrations and guards, and run for this page.

A login returns an actor with capabilities and a trust level, not a role string.

Softanza
NOW = 1700000000   # a fixed clock, as in the guard
a = new stzAuth()
a.Register("dana", "pw")
a.GrantRole("dana", "admin")
tok = a.LoginAt("dana", "pw", NOW)
act = a.ActorOfAt(tok, NOW)
? "user        : " + act.Name()
? "capabilities: " + @@(act.Kinds())
? "posture     : " + act.Posture()
Output
user        : dana
capabilities: [ "effectful", "compute", "sensing" ]
posture     : trusted

The identity-provider sandbox holds a real key and can issue a forged token, so the refusal path is tested before any real provider is involved.

Softanza
NOW = 1700000000   # a fixed clock, as in the guard
idp = new stzOidcSandbox("https://idp.local", "my-app")
rp  = new stzOidcClient("https://idp.local", "my-app")
rp.SetJwks( idp.JwksJson() )        # the provider's public keys
b = new stzAuth()
b.SetOidcClient(rp)
? "forged token   : [" + b.LoginWithOidcAt(idp.IssueForgedIdTokenAt("dana","n-1",NOW), "n-1", NOW) + "]"
? "  why          : " + b.OidcWhy()
Output
forged token   : []
  why          : the signature does not verify against the provider's key

The lanes, one by one

Lanes and their notes are quoted as they were read at the source, on Read from the source on 2026-09-16, from a read-only main worktree.

Request bracket & SLA observability
Strong
Per-request bracket recording http.request.ms/requests/errors and http.route.ms over engine histograms (p50/p95/p99); built-in /health, /metrics, traceparent.histogram.zig; well-known subjects http.request.ms, http.requests, http.errors
Auth, OIDC & sessions
Strong
MountAuth serves login/2FA/magic-link/OTP with HttpOnly+SameSite cookies and CSRF; MountOidcProvider makes the server an IdP; signed requests off-loopback.stzAuth, stzRequestSigner
Stateful service doubles
Strong
Payment state machine (capture-once, refund <= captured), LLM double with cost accounting, mail/SMS sinks, blob store, real-signing OIDC/passkey doubles.stzPaymentsPort; SOFTANZA_SERVICE_VIRTUALIZATION_PLAN.md
Deploy(:Production) refuses fakes
Strong
Every bound service carries a posture; five registry invariants plus graph rules; stzDelivery.Deploy refuses even a fully-entitled human if unsound.base/system/stzDelivery, stzServiceRegistry, stzServiceRule; ~370 assertions under test/system
HTTP server (accept, route, respond)
Solid
Real HTTP/1.1: async accept + framing on the libuv thread, Haro dispatches synchronously (ServeOne/Run), keep-alive; HTTP/1.1 only, single-threaded dispatch.reactor.zig, http_framing.zig, stzAppServer
Routing
Solid
stzAppRouter: Get_/Post/Put_/Delete, path params, trailing * wildcard, exact-first then first-pattern-wins; no route groups, regex constraints or 405 vs 404.stzAppRouter
TLS / HTTPS / mTLS serving
Solid
StartTls/StartHttps with mbedTLS termination below the router and mutual TLS (bRequireClient + CA path); test certs only, no managed cert lifecycle.
Auto-CRUD backend (MBaaS)
Solid
Expose/ExposeWithKey generate REST CRUD over sqlite (/api/<table> list/count/read/create/update/delete); sqlite-only, no relations, filtering or pagination.stzAppBackend, db.zig
HTTP mocking (record / replay / journal)
Solid
stzHttpSandbox: Script matching, record/replay keyed by sha256(method|url|body), strict by default, a journal; no header/body/regex matchers, no latency knob.stzHttpSandbox, stzHttpPort
Request & response objects, body parsing
Partial
stzAppRequest (Query/Header/Body/Param, form-urlencoded) and stzAppResponse (Status/Header/Json/Text/Html/Send); no JSON body parsing, multipart or streaming.stzAppRequest, stzAppResponse
Modern API table stakes
Partial
/health and /metrics ship; WebSocket serving, OpenAPI, content negotiation, rate limiting, templating absent; static files registered but never served.
Middleware pipeline
Emerging
Use/AddMiddleware store handlers in @aMiddleware but _Dispatch has no execution path for them: registered but never invoked.stzAppServer _Dispatch / @aMiddleware

The functions, by what they do

Testing and checking

  • IsRunning server lifecycle in stzAppServer
  • IsObserved routing interface in stzAppServer
  • IsGoverned governance + cross-part audit in stzAppBackend
  • IsReachable Is the far backend actually answering? (stzAppServer serves /health with no route declared, so this needs nothing from the model.) in stzAppBackend
  • IsSandbox a double declares itself -- see stzServiceRegistry in stzPaymentsSandbox
  • IsEphemeral a directory survives a restart in stzFileBlobStore
  • IsLocalReal a genuine local equivalent, not a fake -- see stzServiceRegistry's postures in stzFileBlobStore
  • HasRoute Exact-only presence check (kept for back-compat / introspection). in stzAppRouter

Finding

  • LastMs The duration of the last crossing (ms, monotonic clock) -- the marshalling cost of one Create/Rows/RowCount, either mode. in stzAppBackend
  • LastStatus The HTTP status of the last crossing, either mode (0 = it never completed). 401 here means the far side refused the signature. in stzAppBackend
  • LastRoundtripMs governance + cross-part audit in stzAppBackend

Counting and measuring

  • MeanCrossingMs Mean crossing cost over the whole ledger (refusals, at 0 ms, excluded -- they never crossed). in stzAppBackend
  • NumberOfCallsTo how many times a URL was asked for -- the assertion that catches an N+1 or a retry storm. in stzHttpSandbox
  • NumberOfCalls COST: the fee-free promise, made measurable in stzLlmSandbox
  • Size listing, the S3 idiom in stzFileBlobStore

Replacing and setting

  • SetAgentSlice How long a single serve slice may park on the socket before due agents are ticked. Smaller = crisper agent timing, more loop turns. in stzAppServer
  • SetSecureCookies Add Secure to the auth cookies -- TRUE whenever the listener is TLS, so the session cookie never travels in clear text. in stzAppServer
  • SetPhase the phase -------------------------------------------------------- :development / :emulated -> sandboxes are expected. :production -> they are a violation. The phase is the SAME switch stzDelivery already uses, so nothing new decides what is real. in stzServiceRegistry
  • SetActor Bind the acting actor: cross-part WRITES then require an effectful one (an LLMActor reads the whole solution and commits none of it). Reads are sensing and stay open. Unbound = ungoverned (dev). in stzAppBackend
  • SetSigningKey The shared secret that authenticates the crossing. Set it on BOTH sides: the HOST uses it to require a signature, the CLIENT to produce one. It is the same secret, so this one call serves both roles -- which is also why a real deployment must deliver it out of band (env, vault, stzSecretStore), never in the model file or the command line. in stzAppBackend
  • SetStrict strictness in stzHttpSandbox
  • SetFallback A catch-all answer, for pipelines where the text does not matter and only the SHAPE does. Setting one turns strictness off for unmatched prompts. in stzLlmSandbox
  • SetParams Route path params (bound by the router: /user/:id -> Param("id")). in stzAppRequest

Removing

  • Delete routing interface in stzAppServer
  • Remove S3's DELETE is idempotent: removing what is not there SUCCEEDS. Kept, because a test that asserts otherwise would be asserting a fiction. in stzFileBlobStore

Converting

  • ParseHttpRequest Parse one complete HTTP/1.1 request (the engine frames it: full headers + Content-Length body, CRLF line endings). in stzAppServer
  • AsRuleGraph NOTE this does NOT duplicate the invariants above. Findings from Findings() already carry the report's shape, so the registry joins the shared CI gate directly: oReport.IngestLegacy(oReg.Findings(), "services"). What the GRAPH adds is the question a flag check cannot ask -- which PART of a solution depends on a fake -- and that needs the delivery's parts joined to these nodes (see stzDelivery.AsRuleGraph and stzServiceRuleSet). in stzServiceRegistry

Showing, drawing and formatting

  • Show governance + cross-part audit in stzAppBackend

Reading and writing

  • SaveModelTo Cells carry their TYPE (n/s) rather than being sniffed on the way back in: a price must stay a NUMBER for the revenue maths, and "looks numeric" is exactly how "007" silently becomes 7 -- a defect this library already paid for once in the CSV reader. Fields are percent-escaped . in stzAppBackend
  • Save the PORT contract ------------------------------------------------ Overwrites silently when the key exists, exactly as S3 does. in stzFileBlobStore
  • SaveFile large payloads, without passing through RAM in stzFileBlobStore

Walking and applying

  • Run Serve forever (until the process is killed or Stop() is called from a handler). The documented blocking entry point. in stzAppServer
  • RunFor With agents hosted, the serve slice is BOUNDED: ServeOne(nLeft) would otherwise park on the socket for the whole remaining time whenever no request arrives, and the agents -- which live on this same loop -- would never tick. So we serve for at most @nAgentSliceMs, then tick whatever is due, and repeat. Requests and perceive-decide-act interleave on ONE loop. in stzAppServer
