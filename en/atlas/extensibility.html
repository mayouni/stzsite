Extensibility & foreign code

Strong at consuming foreign libraries, pragmatic at bridging; the plugin, FFI and embed plane is mostly planned.

1 S2 So3 P6 E

Measured against: FFI · Pyodide · Folders: base/plugin · base/extercode · base/extincode · The original Atlas page

The most honestly-mixed group in the survey. Softanza consumes a large, carefully-vendored foreign-code stack (tree-sitter, SQLite, curl, mbedTLS, zlib, ggml, RmlUi, HarfBuzz, PCRE2, all compiled from source) and bridges pragmatically to Python/R/Julia/C/Prolog/Node by subprocess, but the extensibility the group is named for is overwhelmingly planned: no in-process FFI, no embedded interpreter, and the plugin plane ('a plugin is governed foreign capability') is a detailed plan with a recovered reference archive but zero live code.

What a maker does with it, and what stands out

  • Strong foreign-code integration: a dozen serious native libraries built from source with no runtime dependencies
  • Governed foreign capability (designed): accept code you don't trust, audit what it did, undo it
  • SQL-in-Haro and paste-and-tweak foreign-syntax shims
  • The recovered 2024 plugin system proves per-call VM-state isolation works (~3.1 ms/call)

What is owed

  • Fix the red interop suites (C22 duplicate shim definitions, 0 passing)
  • Build the plugin plane (PL0-PL5)
  • In-process FFI (dlopen / cffi-style)
  • Configurable toolchain discovery (retire the hardcoded d: interpreter paths)

No example run on this page. The Python bridge requires a declared execution posture and was not exercised tonight; rather than an unrun block, the page points to the repository's narration on the bridge to Python.

Foreign-library consumption (the vendored stack)
Strong
A vendored C/C++ stack compiled from source via Zig (tree-sitter, SQLite, curl, mbedTLS, zlib, ggml, RmlUi, HarfBuzz, PCRE2); no external runtime deps
Foreign-code parsing (tree-sitter)
Solid
stz_polyglot parses Python and JavaScript (vendored grammars, no interpreter) into a declaration/call protocol feeding stzCodeGraph; two grammars, parse-onlystz_polyglot
External-tool bridges
Solid
Subprocess bridges stzDotCode (Graphviz dot), stzQmlCode (Qt qml runtime), stzImgToAscii (vendored im2ansi.exe); stzImgToAscii ships but is never loaded
Call-out interop (extercode)
Partial
stzExterCode runs Python, R, Julia, C, Prolog and Node via temp file + stzSystemCall + eval(); subprocess-only, hardcoded d: paths, suite currently redtest/extercode (red)
Foreign-syntax shims (extincode)
Partial
Haro shims to paste Python, PHP, C#, Perl, C ternaries and SQL-in-Haro over stzTable; shims not a runtime, the JS shim is an empty stub, suite redtest/extincode (red)
Interop robustness (test state)
Partial
Both interop suites have real assertions but are entirely red: C22 function-redefinition, 0 passing (echo/range0 defined in both PHP and Python shims)test/extercode + test/extincode
In-process FFI
Emerging
None for user code: no dlopen / cffi / direct-C-call surface; the only call-out is the subprocess bridge, an order of magnitude heavier
Embedded interpreters (Pyodide-style)
Emerging
None: no in-process Python / JS / Lua interpreter embedded in the engine; foreign execution is subprocess-only
Plugin plane -- load / register / govern
Emerging
A plan of record (PL0-PL5) and a recovered/ archive marked reference-only; state_* VM primitives exist; no live code, not loaded, no test dirSOFTANZA_PLUGIN_PLAN.md; recovered/ 2024 system (~3.1 ms/call)
Governance of untrusted capability
Emerging
Designed five-clause contract: isolation, per-call ledger, cooperative constraint, currency, governance; XfU reversal and @plugin_author provenance; unbuilt
Isolation & sandboxing
Emerging
Designed two-tier isolation (:State state / :Process reactor spawn); explicitly refuses to be a syscall-level security sandbox; unbuilt
Distribution -- package / marketplace / signing
Emerging
None, and the plugin plan explicitly states it is not a package manager, marketplace or code-signing scheme; deliberately deferred
