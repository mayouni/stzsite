Why a feature exists

Seven design goals

A feature that serves no goal is refused, and a goal with no feature is a gap. Seven goals have held Softanza's design together since 2022. This page lays each against the features that serve it, with the state of each today.

Four vocabularies tell Softanza's design, and they answer four different questions. A goal says why a feature exists. A principle says what Softanza believes. A convention says how code is written. A law says what the tree refuses. This page is the first: the reason, which a reviewer can read goal by goal instead of line by line.

The 2022 slide laid seven goals against thirty-three features. Here they are redrawn with the state of each feature today, and one run per goal.

Of 33 features: 24 built, 4 transformed with the project, 2 changed form, 1 partial, 1 archived, 1 a name only.

1 · Expressiveness

Say what you mean in the shortest honest sentence.

  • Fluent design built · 956 fluent-form tags; RemoveQ()
  • Semantic precision built · the case dial and the suffix grammar; the error catalogue
  • Named parameters built · 94 test files; the hash form of the error raiser
  • Alternative functions built · 4,489 alternative-form tags
  • Multilingual functions archived · names only in the monolithic archive

Expressiveness: one verb in three forms, each saying what happens to the list.

Softanza
o1 = new stzList(L(' "♥1" : "♥3" '))
# the passive form returns a copy and keeps the original
? @@( o1.ItemsReversed() )
? @@( o1.Content() )
# the active form changes the list itself
o1.Reverse()
? @@( o1.Content() )
# the fluent form changes it and lets the sentence go on
o1 = new stzList(L(' "♥1" : "♥3" '))
? o1.ReverseQ().ToStzListOfStrings().ConcatenatedUsing("~")
Output
[ "♥3", "♥2", "♥1" ]
[ "♥1", "♥2", "♥3" ]
[ "♥3", "♥2", "♥1" ]

7 · Manageability

Know why it failed, how fast it ran, and what it did, without leaving the code.

  • Informative error messages built · an error carries Where, What, Why and Todo
  • Visualised call stack a name only · no file builds it; the trace-context module is a different thing
  • Measurable performance built · the performance plane, six strong lanes; the profiler
  • Cachable functions and objects changed form · the decorators are gone; a cache class and an engine cache replace them
  • Loggable functions changed form · the decorators are gone; a log class is used in 30 files

Manageability: an error says where it happened, what, why, and what to do about it.

Softanza
try
	StzRaise([ :Where = "Greeting()", :What = "no name was given", :Why = "a greeting needs someone to greet", :Todo = "pass the name as the first parameter" ])

What the tally says

The skeleton held: most features exist as declared, and the ones that changed did so for stated reasons, such as the host language moving to Haro. Manageability is the goal that drifted most. Its visualised call stack is a name and nothing was built under it, and the decorator forms of caching and logging gave way to classes. A design that drifted deserves a decision and not a silent replacement: either the decorators return as tags the engine honours, or the class form is declared final and this table is amended. That decision is the author's.

The goals are written in thousands of comment tags above method definitions, in about ninety spellings, and no check yet reads them.
